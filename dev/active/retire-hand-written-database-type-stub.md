# Seed: Retire the hand-written `Database` stub in `supabase.service.ts`

**Origin**: Noticed while binding the email-lookup row types to the generated schema types (PR A of the email-status-lookup work, 2026-07-29).

**Priority**: Low — inert today, but actively misleading to readers.

## Problem

There are two exported types named `Database` in the frontend:

1. **`frontend/src/types/database.types.ts`** — the real one, generated by
   `supabase gen types typescript --linked` and kept byte-identical to
   `workflows/src/types/database.types.ts` per
   `infrastructure/supabase/CLAUDE.md` § "Supabase-Generated TS Types".
2. **`frontend/src/services/auth/supabase.service.ts:22`** — a hand-written stub
   carrying the comment *"Define your table types here as you create them"*.

(Neither is AsyncAPI output — that pipeline emits event payloads to
`src/types/generated/generated-events.ts`.)

**The stub describes tables that do not exist.** It declares `public.medications`
and `public.clients`; there are zero occurrences of `medications` in the
generated types and zero `CREATE TABLE ... medications` in `20260212010625_baseline_v4.sql`.

It is also inert:
- Never imported anywhere — `export`ed, but referenced only inside its own file.
- Nothing in `src/` calls `.from('medications')` or `.from('clients')`.
- Every RPC path casts past it: `apiRpc`/`apiRpcEnvelope` do
  `this.client as AnySchemaSupabaseClient` (`SupabaseClient<any, any, any>`)
  before `.schema('api').rpc(...)`, precisely because the stub does not describe
  the `api` schema.

So `SupabaseClient<Database>` at `:74`/`:80`/`:88` provides no real type safety —
it is a placeholder that outlived its purpose and now shadows the generated type
by name.

## Proposed

Point `SupabaseService` at the generated type and delete the stub.

**Not a one-liner** — this is why it was not folded into the PR that found it:
the generated `Database` defaults `SchemaName = 'public'` over the full ~1700-line
schema, so `SupabaseClient<GeneratedDatabase>` changes the inferred surface of
`getClient()` for every consumer (notably `.rpc()` calls, which would begin
type-checking against real public-schema functions rather than the stub's empty
`Functions` block). Expect fallout in `SupabaseAuthProvider.switchOrganization`
(`public.switch_organization`) and anywhere else holding a raw client.

Sequence:
1. Import `Database` from `@/types/database.types` in `supabase.service.ts`;
   delete the local `export interface Database`.
2. Typecheck; triage the `getClient()` consumers that newly resolve.
3. Consider whether `AnySchemaSupabaseClient` can narrow now that the real
   `api` schema is describable — it exists to work around the stub's blindness,
   so it may no longer be needed for the `.schema('api')` chain.

## Verification

`npm run typecheck && npm run lint && npm run test && npm run build` from
`frontend/`. No runtime behaviour should change — this is a type-surface-only
refactor; if any call site changes shape, that is a latent bug the stub was
hiding and should be called out rather than cast away.
